JUSTIFICACION DE HERRAMIENTAS USADAS - PROYECTO OPERACION BABEL
================================================================
Fecha: 2026-09-17
Proyecto: Juego web de entrenamiento de idiomas (Ruso / Mandarin) con
frontend HTML+CSS+JS y backend Node.js + Express + PostgreSQL.
Base original: Microsoft SQL Server (database/Babelsqlbase.txt)
Base actual: PostgreSQL (OperacionBabel_PostgreSQL.sql)


1. MIGRACION DE MICROSOFT SQL SERVER A POSTGRESQL
-------------------------------------------------
Estado en el proyecto:
- Origen: database/Babelsqlbase.txt usa T-SQL: CREATE DATABASE ... COLLATE
  Latin1_General_100_CI_AS_SC_UTF8, INT IDENTITY(1,1), NVARCHAR, DATETIME2,
  BIT, GETDATE(), GO, PRINT, dbo.Tabla, CREATE LOGIN / CREATE USER / db_owner,
  SELECT TOP 5, ISNULL, CONVERT(VARCHAR...120).
- Destino: OperacionBabel_PostgreSQL.sql usa SERIAL PRIMARY KEY, VARCHAR,
  TIMESTAMP / DATE, BOOLEAN, CURRENT_TIMESTAMP / CURRENT_DATE,
  CREATE EXTENSION uuid-ossp/pgcrypto, sin GO ni PRINT, esquema public.

Justificacion real de entorno:
a) Costo y licencia: SQL Server requiere licencia comercial en produccion
   (o ediciones Express/Developer limitadas) y esta atado al ecosistema
   Microsoft. PostgreSQL es open-source con licencia PostgreSQL (permisiva),
   costo 0, ideal para proyecto academico / universitario sin presupuesto
   para licencias y sin riesgo legal al publicar en GitHub.
b) Portabilidad: SQL Server esta optimizado para Windows Server. PostgreSQL
   corre igual en Windows, Linux y macOS, y en cualquier VPS barato, Docker,
   Render, Railway, Supabase, Neon. El equipo desarrolla en Windows con
   laptops personales, pero el despliegue y la correccion docente pueden ser
   en Linux; PostgreSQL evita el vendor lock-in.
c) Unicode nativo: el juego maneja cirilico (багаж, оружие), Hanzi (书, 间谍)
   y emojis de rangos/logros. En SQL Server hubo que forzar
   Latin1_General_100_CI_AS_SC_UTF8 + prefijo N'...' en cada literal.
   PostgreSQL usa UTF-8 por defecto (ENCODING='UTF8'), por eso NVARCHAR -> VARCHAR
   y se eliminan los N''. Menos errores de cotejamiento y menos codigo.
d) Tipos mas simples para Node.js: BIT -> BOOLEAN, DATETIME2 -> TIMESTAMP,
   IDENTITY -> SERIAL. El driver `pg` de Node mapea BOOLEAN/TIMESTAMP
   directamente a true/false y Date de JS, sin conversiones manuales.
e) Despliegue y colaboracion con Git: el script .sql de PostgreSQL es texto
   plano ejecutable con psql en una sola pasada, sin comandos de instancia
   (xp_instance_regwrite, ALTER LOGIN sa, sys.dm_exec_connections) que solo
   tienen sentido en una maquina Windows local con SSMS. Eso permite que
   cualquier integrante clone el repo y levante la BD con 2 comandos.
f) Seguridad operativa: en el .txt original la clave 'OperacionBabel2026!'
   quedaba escrita para los logins sa/babeluser y el rol db_owner. En
   PostgreSQL se deja comentado (CREATE USER babeluser ...) y la conexion
   real va por variables .env (DB_USER, DB_PASSWORD, DB_HOST...), que no se
   versionan. Separa codigo de credenciales.

No se pierde nada funcional: las 20 tablas, FKs, CHECKs, indices y seeds se
conservaron 1:1. Solo cambio la sintaxis propietaria por estandar abierto.


2. NODE.JS (ENTORNO DE EJECUCION DEL BACKEND)
---------------------------------------------
Archivos: index.js (bootstrap), src/app.js, src/db.js, db.js (Pool pg).

Justificacion:
a) Mismo lenguaje en todo el stack: frontend y backend son JavaScript.
   El equipo no necesita aprender PHP, Python o C# adicional; reduce curva
   de aprendizaje y permite reutilizar validaciones y formatos de error
   { ok, codigo BBL-*, error } en ambos lados.
b) Modelo asincrono no bloqueante: el juego hace muchas consultas cortas y
   concurrentes (sesiones, flashcards, rachas, errores). Node maneja miles
   de conexiones concurrentes con un solo hilo + event loop, suficiente para
   un curso / demo sin montar un servidor de aplicaciones pesado como
   Tomcat, IIS o .NET.
c) Ecosistema npm/pnpm inmediato: Express, pg, cors, dotenv, nodemon se
   instalan en segundos. No requiere compilar ni configurar un servlet,
   un php.ini o un entorno .NET.
d) Ejecucion local simple: `node index.js` o `pnpm run dev` levanta el API
   en puerto 3000. Cualquier PC con Node 18+ lo corre, sin IIS ni SQL Server
   Management Studio obligatorios.
e) Compatibilidad con hosting gratuito: Render, Railway, Vercel Functions,
   Glitch y VPS aceptan apps Node de forma nativa, mientras que SQL Server
   + backend .NET exigirian VM Windows de pago.


3. PNPM EN VEZ DE NPM
---------------------
Evidencia: pnpm-lock.yaml + package.json -> devEngines.packageManager pnpm ^11.3.0.

Justificacion:
a) Ahorro de disco y velocidad: npm duplica carpetas por cada proyecto en
   node_modules/. pnpm usa un store global con hard links / content-addressable.
   En PCs de estudiantes con disco limitado y en clones repetidos del repo,
   `pnpm install` es 2x-3x mas rapido y ocupa fraccion del espacio.
b) Estrictez de dependencias: npm aplana todo y permite importar paquetes
   no declarados (phantom dependencies). pnpm crea node_modules estricto;
   si falta una dependencia en package.json, falla. Eso evito errores del
   tipo "en mi maquina si funciona" entre integrantes.
c) Bloqueo determinista: pnpm-lock.yaml garantiza que todos instalen
   exactamente Express 5.2.1, pg 8.13.0, cors 2.8.6, etc. Con npm sin lock
   habia deriva de versiones entre entregas.
d) Compatibilidad total: pnpm entiende el mismo package.json y los mismos
   scripts (dev/start/test), por lo que `pnpm run dev` reemplaza 1:1 a
   `npm run dev`. No hay costo de migracion; el README aun menciona npm
   como alternativa para el docente que no tenga pnpm.
e) Seguridad de scripts: pnpm por defecto es mas restrictivo con
   postinstall scripts, reduciendo superficie de supply-chain attack,
   relevante al publicar el repo en GitHub.


4. JAVASCRIPT (VANILLA, SIN TYPESCRIPT NI FRAMEWORK)
----------------------------------------------------
Archivos: Js babel/*.js, Js babel/core/api.js, core/ui.js, src/**/*.js.

Justificacion:
a) Requisito formativo HCI/juegos web: la asignatura pide manipular DOM,
   eventos, fetch y CSS directamente. Usar React/Vue/Angular ocultaria ese
   aprendizaje y obligaria a toolchain (Vite, Babel, JSX). Vanilla JS se
   ejecuta abriendo el .html en el navegador, sin build.
b) Cero compilacion: no hay tsc, bundler ni transpilacion. Cualquier cambio
   en Ahorcado.js, Flashcard.js o Mazos.js se ve con F5. Ideal para
   iteracion rapida en mockups y wireframes.
c) Interoperabilidad total con el backend: el wrapper window.BabelAPI
   (core/api.js) usa fetch nativo contra /api/* y devuelve JSON. No se
   necesita Axios ni SDK; fetch ya viene en todos los navegadores modernos.
d) Modularizacion suficiente sin framework: core/ui.js centraliza sidebar,
   accesibilidad (daltonismo/animaciones reducidas), vidas, logros y
   validaciones; las 9 paginas lo reutilizan. Se logra DRY sin meter 150 MB
   de node_modules de frontend.
e) Costo de mantenimiento bajo: para el alcance real (8 paginas, CRUD de
   usuarios, sesiones, flashcards) TypeScript aportaria poco y exigiria
   tipar 20 tablas. Se priorizo entregar funcionalidad jugable.


5. HTML5 (ESTRUCTURA)
---------------------
Archivos: Babelhome.html, Pages/*.html (8 vistas), legacy/*.html.

Justificacion:
a) Estandar universal: todo navegador lo renderiza sin plugins. Frente a
   alternativas (PDF interactivo, WinForms, Unity WebGL), HTML permite
   entregar el juego como sitio estatico + API, evaluable con doble clic.
b) Semantica y accesibilidad: header/nav/main/section/form/label permiten
   lector de pantalla y navegacion por teclado, exigidas en HCI junto con
   modo daltonico y animaciones reducidas (accessibility.css).
c) Formularios nativos: Login, Enlistamiento e Intendentes usan
   <form>, required, type=email/password, lo que da validacion gratuita
   antes de llegar al backend y sus codigos BBL-VAL-*.
d) Separacion de responsabilidades: HTML solo estructura; estilo va en
   Css Babel/ y logica en Js babel/. Cada pagina es independiente, facilita
   reparto de trabajo por integrante.


6. CSS3 VANILLA (SIN BOOTSTRAP / TAILWIND)
------------------------------------------
Archivos: Css Babel/*.css (11 hojas: por pagina + accessibility.css + responsive.css).

Justificacion:
a) Estetica tematica propia: el juego exige look militar/terminal verde,
   papel envejecido, soviet_style/dynasty_style por idioma. Un framework
   generico impondria su sistema de diseño; CSS propio da control total de
   colores, glitches, sombras y rotacion 180° de flashcards.
b) Peso minimo: Bootstrap (~200 KB) o Tailwind (build + purge) son
   innecesarios para 8 vistas. CSS puro carga instantaneo en red local del
   laboratorio y funciona offline.
c) Responsive y accesibilidad hechos a mano: responsive.css + media queries
   adaptan a movil de gama baja; accessibility.css implementa
   ModoDaltonico y AnimacionesReducidas que exige la tabla
   ConfiguracionUsuario. Con framework habria que sobrescribirlo de todos
   modos.
d) Curva de aprendizaje: la materia evalua selectores, flexbox/grid y
   especificidad. Usar utility-classes evitaria demostrar ese conocimiento.


7. EXPRESS 5 (FRAMEWORK BACKEND)
--------------------------------
Archivo: src/app.js, src/routes/*.js, package.json -> express ^5.2.1.

Justificacion:
a) Minimalista y estandar de facto en Node: con 10 lineas se montan
   middlewares (cors, express.json), 6 routers bajo /api y manejo central
   { errorHandler, rutaNoEncontrada }. Alternativas como Koa/Fastify son
   menos conocidas por el docente; NestJS seria sobredimensionado.
b) Enrutado por recurso: usuarios, auth, administradores, contenido,
   sesiones, perfil. Cada router delega en controller -> service ->
   repository -> db, arquitectura en capas pedida en documentacion.
c) Middleware JSON integrado: express.json() parsea cuerpos sin body-parser
   externo, suficiente para login, registro y guardado de progreso.
d) Compatible con el driver pg: los repositories usan query(text, values)
   con parametros $1,$2, lo que previene inyeccion SQL sin ORM pesado
   (Sequelize/Prisma exigirian migraciones y codegen para 20 tablas).


8. PG (node-postgres) + POOL DE CONEXIONES
------------------------------------------
Archivos: db.js (new Pool, query, getClient), src/db.js re-export, .env.example.

Justificacion:
a) Driver oficial y ligero: `pg` es el cliente PostgreSQL mas usado en Node,
   sin ORM. Permite escribir el SQL migrado tal cual y verificarlo en psql.
b) Pool (max:20, idleTimeout 30s, connectionTimeout 10s): el juego abre
   muchas conexiones cortas (cada flashcard, cada desafio). Crear una
   conexion por request agotaria PostgreSQL; el pool las reutiliza y evita
   error "too many clients" en demo con todo el salon conectado.
c) Consultas parametrizadas ($1,$2...): eliminan concatenacion de strings y
   por tanto inyeccion SQL en NombreClave, contraseñas y busquedas de
   Diccionario con Hanzi/cirilico.
d) Soporte a transacciones: getClient() permite BEGIN/COMMIT para
   operaciones atomicas (ej. cerrar sesion + otorgar logro + actualizar
   Estadisticas). Sin esto habria estados inconsistentes si falla a mitad.
e) Logs operativos: eventos pool.on('connect'/'error') avisan en consola
   "Conexion tactica establecida" o errores de red, util para depurar en
   laboratorio sin APM externo.


9. DISEÑO DE LA BASE DE DATOS (20 TABLAS EN 5 CAPAS)
----------------------------------------------------
Archivo: OperacionBabel_PostgreSQL.sql (672 lineas) + seeds.

Justificacion de entorno, no solo teorica:
a) Capa 1 Catalogos (Idiomas, Rangos, Categorias, NivelesDificultad):
   normaliza lo que antes eran campos libres (Categoria NVARCHAR,
   NivelDificultad INT). Evita 'militar' vs 'Militar' vs 'MILITAR' y permite
   agregar un tercer idioma sin ALTER TABLE, solo INSERT.
b) Capa 2 Contenido (Diccionario, Frases, MazosFlashcards, Flashcards):
   separa palabra (Diccionario) de su presentacion (Flashcards) y de su
   agrupacion (Mazos). Un mismo IdItem puede estar en varios mazos sin
   duplicar traduccion ni audio. AudioUrl y NotasContexto soportan
   pronunciacion y contexto tactico sin columnas nuevas.
c) Capa 3 Usuarios (Usuarios, ConfiguracionUsuario 1:1, RegistrosAlistamiento,
   Logros): ConfiguracionUsuario guarda TemaVisual, Volumen, ModoDaltonico
   exigidos por HCI; RegistrosAlistamiento modela el formulario fisico de
   alistamiento (CodigoAlistamiento AL-xxx); Logros desacopla insignias.
d) Capa 4 Transaccional (SesionesEntrenamiento, DesafiosInfiltracion,
   HistorialErrores, HistorialGameOver): registra cada partida para
   auditoria docente y para repeticion espaciada. CHECKs
   (Vidas 0-5, Estado IN ACTIVA/COMPLETADA/GAME_OVER/ABANDONADA) impiden
   datos imposibles aunque el cliente sea manipulado.
e) Capa 5 Progreso (ProgresoFlashcards con UNIQUE(IdUsuario,IdFlashcard),
   UsuarioLogros, RachaDiaria UNIQUE(IdUsuario,Fecha), Estadisticas 1:1):
   UNIQUEs impiden duplicar progreso; indices (IdUsuario,FechaFallo),
   (ProximaRevision), (Dominada) aceleran las consultas criticas de
   repaso SM-2 sin full scan, comprobable en salon con cientos de filas.
f) Integridad referencial real: ON DELETE CASCADE (borrar usuario borra su
   progreso), SET NULL (borrar categoria no borra palabras), NO ACTION
   (no borrar palabra con flashcards activas). Protege contra borrados
   accidentales desde el panel Administradores.


10. DOTENV + .ENV.EXAMPLE (CONFIGURACION POR ENTORNO)
----------------------------------------------------
Archivos: .env (no versionado), .env.example (plantilla), .env.keys.

Justificacion:
a) Separa codigo de secretos: DB_PASSWORD, ADMIN_SECURITY_KEY y PORT cambian
   entre laptop de cada integrante, PC del docente y servidor. Sin dotenv
   habria que editar db.js en cada maquina y se correria el riesgo de
   commitear la clave real (como paso en el .txt con sa/babeluser).
b) Doce-factor app: la configuracion vive en el entorno, no en el codigo.
   Basta copiar .env.example -> .env y completar 5 lineas para levantar el
   proyecto, documentado en README.
c) Seguridad en GitHub: .gitignore excluye .env y .env.keys; solo se sube
   la plantilla sin valores. Permite repo publico para entrega sin exponer
   credenciales de PostgreSQL local.


11. CORS
-------
Archivo: src/app.js -> app.use(cors()), dependencia cors ^2.8.6.

Justificacion:
a) Arquitectura desacoplada: el frontend son .html estaticos que pueden
   abrirse por file://, Live Server (5500) o Nginx, mientras el API corre
   en :3000. Sin CORS el navegador bloquearia fetch por same-origin policy.
b) Desarrollo por modulos: cada integrante levanta su pagina en distinto
   puerto; cors() Permite probar sin configurar proxy reverso.
c) Deuda conocida: en produccion deberia restringirse a origins
   permitidos; abierto es aceptable solo en entorno academico local.


12. NODEMON (DESARROLLO)
-----------------------
Dependencia dev: nodemon ^3.1.14, script `pnpm run dev`.

Justificacion:
a) Recarga automatica: reinicia index.js ante cada guardado en src/,
   evitando parar/iniciar manualmente durante depuracion de rutas y
   validaciones BBL-*. Ahorra decenas de reinicios por sesion.
b) Solo dev: no va en production (start usa `node index.js`), por lo que no
   penaliza rendimiento ni memoria en despliegue. Es la herramienta estandar
   frente a `node --watch` (mas nuevo y menos conocido por el docente).


13. GIT + GITHUB + .GITIGNORE
-----------------------------
Evidencia: .git/, README.md, pnpm-lock.yaml versionado, node_modules/ y .env excluidos.

Justificacion:
a) Trabajo colaborativo: 20 tablas, 8 paginas y 6 routers no los hace una
   sola persona; Git permite ramas por modulo (ahorcado, flashcards) y
   revision de PRs antes de entrega.
b) Entrega verificable: el docente clona, hace pnpm install, crea .env desde
   .env.example, ejecuta el .sql y `pnpm run dev` + `node test/smoke.test.js`.
   Sin repo seria envio de ZIPs desincronizados.
c) Higiene: .gitignore excluye node_modules/ (se regenera) y .env
   (secretos), manteniendo el repo liviano y seguro.


14. HERRAMIENTAS DE APOYO (VS CODE + TEST SMOKE)
------------------------------------------------
a) VS Code (.vscode/): editor gratuito, multiplataforma, con extensiones de
   PostgreSQL, ESLint y Live Server. Es el comun denominador en laboratorio
   frente a SSMS (solo Windows, solo BD) o Visual Studio (pesado).
b) test/smoke.test.js + `pnpm test`: prueba minima de arranque sin
   frameworks (Jest/Mocha). Verifica que el API responde antes de la demo,
   evitando "funciona en mi maquina" durante la sustentacion.
c) legacy/ y database/: conservan el backup T-SQL, index.legacy.backup.js y
   scripts de seed (populate_flashcards.js, setup_views.js) como evidencia
   del proceso de migracion exigido en documentacion.


CONCLUSION
----------
Cada herramienta se eligio por restriccion real de entorno academico:
costo 0 (PostgreSQL, Node, pnpm, VS Code), portabilidad Windows/Linux,
instalacion en minutos, mismo lenguaje en ambos lados, y trazabilidad
Git + .env para evaluacion. La migracion SQL Server -> PostgreSQL no es
capricho: elimina licencias, simplifica UTF-8 para ruso/chino, y hace
desplegable el proyecto fuera del laboratorio Windows.
